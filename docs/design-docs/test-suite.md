# The test suite

Three homes, three questions.

| Home | Question | Cost model |
| --- | --- | --- |
| `tests/dst.rs` | Do the durability invariants hold under any schedule of agents, conflicts and crashes? | In-process server, in-process clients, no subprocesses. A seed reproduces a failure exactly. |
| `tests/properties.rs` | Does every value survive its own encoding, and does every decoder survive arbitrary bytes? | Pure, generated by proptest. Milliseconds. |
| `tests/integration.rs` | Does the product work when it is real processes, real sockets, real git? | Subprocesses. Kept only where the subprocess *is* the coverage. |

Shared code lives in `tests/support/` (the simulation: cluster, agent, oracle,
schedule, rng) and `tests/common/` (the subprocess helpers: command runners,
retry/settle, bucket harness, deadline line reads).

## Rules of thumb

- A new invariant about heads, WAL entries, the index or convergence belongs in
  the DST oracle, not in a new integration test. The oracle runs after every
  generated step, so one assertion there is checked hundreds of times a run.
- A new encoding or a new decoder gets a round-trip property and a
  never-panics-on-arbitrary-bytes property, both in `tests/properties/`.
- A new integration test needs an answer to "what does the subprocess give me
  that the simulation cannot?" Real signals, real git, real CLI plumbing, and
  genuine OS-level concurrency are good answers. "It is how the last one was
  written" is not.
- No fixed sleeps. Wait for the thing: `common::lines::Lines` for a child's
  output, `common::workspace::wait_for` for server-side state.
- The client disk cache is **off** in the in-process suites
  (`support::isolate_process_environment` sets `TANDEM_DISABLE_CACHE`). One
  address space holds every client of every server, so a cache shared by all of
  them could answer the oracle's "every byte reads back over the wire, out of a
  store that has not seen it before" from local disk, and the invariant would
  stop meaning anything. The integration suite keeps it on and pins
  `TANDEM_CACHE_DIR` inside each test's home; `integration/client_cache.rs` is
  where the cache itself is the subject.

## What the oracle cannot see, and what closes every schedule

The oracle runs after every step and asks about the state as it is *then*. Two
invariants have no answer at that moment, so `schedule::close` runs after the
last step of every schedule, generated or fixed:

1. **Objects the server took in but no entry has carried.** An object staged
   between two attempts of a retried publish, or drained by a publish whose WAL
   write then failed, belongs to whichever publish comes next — so mid-schedule
   there is nothing to assert yet. `close` makes one publish to drain them, then
   asserts the exact bytes appear inside some WAL entry. The oracle's index/WAL
   check does not cover this: it asks whether every *head* has an entry, and an
   object has no head of its own.

   The claim is scoped to one process. The staging buffer is memory on purpose,
   and an object in it belongs to a publish nobody has been told succeeded, so a
   server that dies holding one owes nothing — the client's operation failed and
   it will write the objects again. The harness therefore forgets what it is
   waiting for whenever the server goes away, and what is left is the invariant
   that matters: while one process lives, nothing it drained is lost.
2. **WAL completeness.** Every restart until then keeps the materialized repo,
   and the server answers reads out of it, so an object that reached the
   server's disk but no WAL entry stays readable and the gap stays invisible.
   `close` throws that disk away and boots from the bucket alone, then runs the
   oracle again. `Step::ColdRestart` does the same mid-schedule.

## Fault injection

Faults used to be `TANDEM_TEST_*` environment variables read by the server
process, which meant only a spawned server could be faulted and only the three
windows somebody had written a variable for existed. They are now an injectable
seam: `jj_tandem::server::FaultPoints`, handed to `Server::new_with_faults`.
The DST arms them from a seed, so every window in the durability order is
enumerable rather than hand-picked:

`BeforeWalWrite`, `AfterWalWrite`, `AfterIndexWrite`, `AfterLocalApply`,
`AfterMetadataWrite` — plus index-CAS conflicts, an object staged between two
attempts of a retried publish, a bucket that refuses the next WAL entries, a
failing derived-head WAL write, and a head reconcile that degrades to leaving
the heads unmerged.

One of those is also reachable from the environment, and the exception is worth
stating because the rule above is otherwise absolute.
`FaultPoints::from_environment` reads `TANDEM_TEST_FAIL_RECONCILES` once, when
a server process starts, and
nothing reads it again. It exists for the one thing a value cannot reach: a
`tandem serve` that a *subprocess* test spawned, where the test holds no handle
in the server's address space to arm. `tests/integration/clone.rs` needs it,
because what it is testing — a workspace pointer decided by a merge of heads
that outlived the publish that made them — has to be driven through the real
binary, the real clone, and a real interruption. An in-process test arms the
value directly and sets nothing.

A crash makes the in-process server return an error and set a `halted` flag;
the harness then restarts it over the same repo and bucket. From a client's
point of view and from the invariants' point of view that is the same event as
`process::exit(99)`, and unlike a real exit it can be driven from a test.

## Authority

Who may publish what is checked in three places, and the split follows the
rules of thumb above:

- `src/auth.rs` unit tests: a token is minted, read back, and refused once it
  has expired or once a byte of it is changed. Pure, so it lives with the code.
- `src/server/scope.rs` unit tests: the view-diff rules themselves, as views in
  and a verdict out. No repo, no server, no HTTP.
- `tests/integration/auth.rs`: the same rules as a person meets them — real
  HTTP for the 401/403/409 answers, and real `tandem bookmark create` through a
  real workspace for the "own namespace yes, `main` no" matrix, which is the
  part only a subprocess can give.

The DST covers the other half: every generated publish goes through the same
scope check as a real one, so a rule that refuses honest work fails a seed
rather than a hand-written case.

## Hoisted helpers

Six copies of the same three helpers lived in six test files. One copy each now
lives in `tests/common/workspace.rs`: `run_tandem_resilient` (with
`is_retriable_workspace_state` and `hinted_op_integrate_id`), `settle_workspace`,
`find_commit_id` (with `find_commit_id_on_server` and the `first_commit_id`
parser the two share), and `wait_for`. The rest of the shared surface:

- `common::ServerFixture` is the setup nearly every integration test opened
  with — temp directory, isolated home, server repo, free port, spawn, wait —
  and the `Drop` none of them had. A test that panics now takes its server with
  it instead of leaving it running. `common::bucket_harness::BucketHarness` is
  the same idea for the tests that need a bucket as well.
- `common::workspace::wait_for` subscribes to the server's `/api/events` stream
  and probes when an event arrives. It replaced waiters that spawned a `jj log`
  every fifty milliseconds — up to three hundred processes to observe one
  change.
- `common::lines::Lines` owns a child's pipe on a thread and hands the test a
  deadline read. It replaced fixed sleeps in the watch, log-streaming and
  contention tests. `common::lines::start_log_stream` subscribes to a daemon's
  log over its control socket and hands back both halves.
- `tests/jj-test-config.toml` is the jj configuration both suites run under.
  `tests/common` and `tests/support` serve different binaries and cannot call
  each other, so they `include_str!` the same file rather than keeping two
  literals that would drift.

## Wall clock

| | Binaries | Tests | Full `cargo test` |
| --- | --- | --- | --- |
| Before | 23 | 101 | ~27 s |
| After | 3 | 99 | ~10 s |

Cargo runs test *binaries* one after another and the tests *inside* one binary
in parallel, so collapsing 23 binaries into 3 is most of the difference. The
rest came from deleting duplicated coverage, from replacing sleeps with
deadline reads, and from making the five-agent contention test read its files
in parallel instead of one subprocess at a time.

The "before" figure was measured during this stage, before the restructure, and
has not been taken again since; the "after" figure is the median of five warm
runs. Per binary: lib 0.12 s, dst 3.5 s, integration 4.4 s, properties 1.8 s.
